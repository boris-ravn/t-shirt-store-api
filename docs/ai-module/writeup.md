# AI Module - Write-Up

**Repository / PR:** [boris-ravn/t-shirt-store-api](https://github.com/boris-ravn/t-shirt-store-api), branch [`feat/ai-skills`](https://github.com/boris-ravn/t-shirt-store-api/tree/feat/ai-skills) ([compare against `main`](https://github.com/boris-ravn/t-shirt-store-api/compare/main...feat/ai-skills)) — pushed, PR opened.

**Starting commit:** [`651d55f`](https://github.com/boris-ravn/t-shirt-store-api/commit/651d55f6ffa4c87ad29a19f0c45210482e41d2ab) — `Merge pull request #18 from boris-ravn/feat/brevo-smtp`, the tip of `main` before any AI-module work began.

**Improvement:** Every auth notification email (`AuthService.resetPassword`'s `sendPasswordChangedEmail`, `forgotPassword`'s `sendPasswordResetEmail`) was called unguarded. Two real bugs followed: an SMTP failure during `resetPassword` reported an already-successful password change as a 500 with no way for the client to recover, and the same failure in `forgotPassword` broke its documented user-enumeration-resistance contract (only the *existing-account* path could then 500, while the unknown-email path always resolved 202). Fixed by wrapping both calls in try/catch and logging via a new `Logger` on `AuthService`, matching the existing post-commit best-effort pattern already used in `StripeWebhookService`. I know it works because I reproduced the exact failure first (checked out the pre-fix `auth.service.ts` against the *post-fix* test file and watched 2 of 16 tests fail with `Rejected to value: [Error: SMTP unreachable]`), then restored the fix and watched all 16 pass — a real, captured before/after, not an assumption. Lint, build, and the full `npm run test:e2e` suite (real Postgres/Redis/Mailhog/MinIO via `docker compose up -d`) all pass on top of it: 35/35 e2e tests, including the Redis-dependent low-stock notification test.

## Skills

| Skill (file link) | Goal, inputs → steps → output | Exact invocation |
| --- | --- | --- |
| [`observability`](../../.claude/skills/observability/SKILL.md) | Goal: proactively surface error-handling/logging gaps around external-service calls before they turn into a reported bug. Input: a scope (module, directory, or the whole app). Steps: enumerate every call to Stripe/mail/S3/BullMQ in scope → check each site for a `try`/`catch`, `Logger` usage, and whether a failure maps to the project's RFC 9457 shape → rank by real severity (false-failure-on-success > invisible-but-handled > already fine). Output: a ranked findings list only — explicitly never a fix. | `/observability Sweep the whole app for error-handling and logging gaps around external-service calls (Stripe, mail, S3, BullMQ).` |
| [`investigate-task`](../../.claude/skills/investigate-task/SKILL.md) | Goal: turn one finding or bug report into an implementation plan before any code is written. Input: a finding/bug description. Steps: read the governing docs for the area touched (`architecture.md`, `decisions.md`, `docs/api/`) → find the real code and its existing test coverage → surface every "it depends" decision explicitly instead of picking silently. Output: a plan (context, approach, test plan, open decisions) — never code. | `/investigate-task Investigate the top finding from the observability sweep: [the finding text, pasted in full]` |
| [`verify-fix`](../../.claude/skills/verify-fix/SKILL.md) | Goal: prove a fix works with real, captured output instead of a claimed result. Input: the finding plus the already-implemented fix. Steps: reproduce the failure against the pre-fix code → re-run the identical check against the fixed code → report a straight before/after table, marking anything that couldn't be run as "not run," never as passing. Output: a before/after table with pasted terminal output. | `/verify-fix Verify the fix for the finding we solved: show the relevant test/check failing before the fix and passing after, real output only.` |
| [`docs-sync`](../../.claude/skills/docs-sync/SKILL.md) | Goal: catch documentation drift right after a code change lands, before it becomes someone else's problem to discover. Input: a scope (a module, a commit range, or the whole `docs/` tree). Steps: match the scope to the doc(s) that govern it → read the doc and the current code side by side → classify each mismatch as doc-stale, code-stale, or genuinely unclear. Output: a drift report with proposed doc edits only — never a code change. | `/docs-sync Check whether docs/architecture.md and docs/decisions.md are still accurate after the fix.` |
| [`research-options`](../../.claude/skills/research-options/SKILL.md) | Goal: replace a training-data guess about a library's current API/behavior with a cited, verified answer. Input: a specific API/behavior question, or two-plus candidate approaches to compare. Steps: fetch current docs/source for the dependency in question → cite a doc URL or a `file:line` in this repo → produce a short decision brief. Output: a cited brief, not an implementation. Exercised in a cold fresh-session run (see evals.json) against the actual inline-vs-queue question this improvement raised, and separately against a CASL `manage`-wildcard claim in `architecture.md` — not part of the assessed pair, but verified working, not just designed. | `/research-options <the specific API/behavior question, or the approaches to compare>` |

**Assessed pair:** `observability` and `verify-fix` are the two skills this module is assessed on — they're the ones exercised end to end against the improvement below, including a cold (fresh-session) re-run of each with no memory of this write-up's own claims. `investigate-task`, `docs-sync`, and `research-options` are supporting/exploratory: built to the same standard and each cold-run-verified in isolation (see Evidence), but not the assignment's required pair.

**Notes:** All five skills live in `.claude/skills/` and are written specifically for this repo, not generic templates — each one's trigger description cites this repo's own `CLAUDE.md`/`docs/` conventions, and each has a stated "failure mode to avoid" so the five don't blur into each other's job (`observability` never proposes a fix; `investigate-task` never writes code; `verify-fix` never invents output; `docs-sync` never edits code). The four report-only skills (`docs-sync`, `investigate-task`, `observability`, `research-options`) now enforce that in frontmatter, not just prose, via `disallowed-tools` (Bash/Edit/Write/NotebookEdit, or Edit/Write/NotebookEdit for `docs-sync` which still needs Bash to run `npm run lint:openapi`) — `allowed-tools` was considered first but the actual [Skills docs](https://code.claude.com/docs/en/skills) show it only pre-approves tools for one turn and restricts nothing, so `disallowed-tools` is the one that's real. Reused tooling: this project's own `npm run lint`/`build`/`test`/`test:e2e`/`lint:openapi` scripts (no new test runner or CI added), and `docker compose up -d` for the real local Postgres/Redis/Mailhog/MinIO stack. Setup: no extra install beyond what the repo's own `README`/`CLAUDE.md` already document — the skills are plain markdown files read by Claude Code, nothing to build or deploy.

Safety/rollback: every skill is either read-only (produces a report/plan) or gated behind this repo's existing plan-approval workflow before any code is written (`CLAUDE.md`'s "plan, then implement" rule) — no skill here commits, pushes, or runs a destructive command on its own. The actual fix landed as small, reviewable, revertable commits (see Evidence below); nothing was force-pushed, no migration was run, and `git commit`/`push` only happened when I explicitly asked for it, per this repo's own hard rules.

## Project Results

**Before → after:** Before, a gap like this would surface reactively — a bug report, or a reviewer catching it in review — and the "what's wrong," "what to do about it," and "does it actually work" steps would typically get mixed into one pass. That's exactly the failure mode this repo's own `CLAUDE.md` warns about elsewhere (a past doc summary drifted and asserted a removed column within a day). With the skills: `/observability` surfaced **8 ranked findings** across every Stripe/mail/S3/BullMQ call site in one sweep, including two genuinely subtle ones — a dropped low-stock-notification enqueue that *looks* retryable via BullMQ but isn't (the retry short-circuits into a no-op once the order is no longer `pending`), and a fully silent `.catch(() => {})` around Stripe cleanup calls with zero logging anywhere. `/investigate-task` turned the #1 finding into a plan that named three real "it depends" decisions instead of picking silently: where the new logging should live (inline in `AuthService` vs. centralized in `MailService`), whether to fix the sibling `forgotPassword` bug in the same change, and unit-only vs. real-SMTP-failure e2e verification — I answered each via `AskUserQuestion` rather than the skill assuming. `/verify-fix` produced actual pasted Jest output (2 failing → 16 passing) instead of a claimed "it works." `/docs-sync` caught that the fix needed a new `docs/decisions.md` entry per this repo's own stated documentation policy, and separately surfaced an unrelated, pre-existing stale line in `architecture.md` (the Mail stack row hadn't been updated when authenticated-SMTP-relay support shipped in an earlier PR).

What needed my judgment, not the skills': whether to bundle `forgotPassword`'s fix into the same change as `resetPassword`'s (yes — same root cause, same file); and exactly where the new `Logger` should live. A separate, same-session doc-maintenance pass had also pruned `docs/decisions.md` by ~54% — that pass wasn't run through one of the five packaged skills, wasn't part of either required deliverable, and mentor review correctly called it out as scope creep bundled into an unrelated PR. It's been reverted on this branch and moved to its own branch (`chore/decisions-cleanup`) for a separate PR — the lesson being that "I did this in the same session" isn't the same as "this belongs in the same PR," and a packaged skill (`docs-sync`, or a `git status`/scope check before committing) would have caught the drift in scope, not just drift in docs.

**Limitations:**
- `verify-fix`'s before/after procedure assumes a single-commit, single-test fix reproducible with a Docker-free unit check; a cold run surfaced that it has no guidance for a fix spanning multiple commits/tests, or for a worktree missing installed dependencies/generated code (both were worked around, not blocking — see `evidence/verify-fix-cold-run.md`) — worth a follow-up revision beyond this review cycle.
- `verify-fix` also has no guidance for a "confirm the contract is still valid" check with no actual diff to reproduce a before-state from (eval 2's cold run had to drop the before/after table to a single-state check) — same follow-up.
- `docs-sync`'s revised module-name resolution (a `git log` on the module's own directory) can still pick the wrong baseline commit when the actual behavior lives partly outside the named module's directory (found by a cold run on the promo-redemption case) — the fix in this PR narrows the original gap but doesn't fully close it.
- The real e2e suite (`npm run test:e2e`) needs a Docker daemon. Docker was unavailable on this machine for most of this remediation session, so the `verify-fix` cold runs correctly reported it as "not run — no Docker daemon available" rather than skipped or faked (see `evals/evals.json` and `evidence/verify-fix-cold-run.md` — those are accurate records of what actually happened in those specific runs, left as-is rather than rewritten). Docker was brought up afterward and the full suite was run for real, 35/35 passing — see [`evidence/e2e-full-suite.txt`](evidence/e2e-full-suite.txt) — but that run doesn't add before/after coverage for the auth-mail fix itself, which (per the cold `investigate-task` run) has no dedicated e2e coverage at all, only unit tests.
